# 프로젝트 개요

이커머스(쿠팡 등) 생활용품 카테고리에서 경쟁 제품을 분석해, "가성비 포지셔닝"으로
신제품을 기획하기 위한 리서치 자동화 도구. 간헐적으로 (필요할 때마다) 실행하는
용도이며, 매번 처음부터 설명하지 않아도 되도록 이 파일에 맥락을 남겨둠.

## 전체 작업 흐름 (5단계)

1. 특정 채널·카테고리의 상위 20~25개 제품 썸네일을 폰으로 캡처
2. 썸네일에서 브랜드명/용량/구성/판매가/단위당단가/제품형태(용기·리필파우치·말통 등) 추출
   → **`analyze_thumbnails.py`로 구현 완료**
3. 추출된 데이터를 바탕으로 시장 내 우선 타겟 스펙(형태/용량/가격대) 도출
   → 사람이 엑셀 보면서 판단 (자동화 대상 아님, 매번 상황이 다름)
4. 타겟 제품군의 상세페이지를 통으로 캡처해서 USP 분석
   → **미구현, 다음 작업 대상**
5. 결과물을 엑셀 또는 제품기획서(docx) 형태로 출력

## 현재 구현 상태

### `analyze_thumbnails.py` (2단계, 완료)
- 폴더 안 이미지들을 하나의 배치로 묶어 Claude Vision(`claude-sonnet-5`)에 전달
- AI 역할: 이미지 속 텍스트 읽기 + 제품형태(본품/리필/말통) 시각적 판단만 수행
- **출력 형식은 Structured Outputs로 강제** — `ProductInfo`(pydantic) 스키마를
  `client.messages.parse(output_format=...)`에 넘기면, API가 스키마를 벗어난
  응답 자체를 만들지 못하게 막아줌. 덕분에 코드블록 제거·`json.loads`·파싱 실패
  처리가 전부 불필요해졌음. 추출 항목을 바꾸려면 `ProductInfo`만 고치면 됨
  (항목 설명도 `Field(description=...)`에 적으므로 프롬프트는 원칙만 담당).
- 타입을 스키마에 못박은 덕에(`price_krw: int | None`) 판매가에 쉼표나 '원'이
  섞여 들어오는 일이 없음 → 뒤의 나눗셈이 안전함
- **숫자 계산(단위당단가 등)은 반드시 파이썬 코드에서 처리** — AI가 산수를 틀리는 걸
  방지하기 위한 의도적 설계. 이 원칙은 앞으로 만들 스크립트에도 유지할 것.
- **호출 경로는 Anthropic 공식 CLI(`ant`)** — 파이썬이 요청 JSON을 만들어
  `ant messages:batches {create,retrieve,results}`에 stdin으로 넘김. 인증은
  `ant auth login`(OAuth 프로필)이 담당하므로 ANTHROPIC_API_KEY가 필요 없음.
  이 때문에 anthropic SDK 의존성도 없앰(스키마는 pydantic만으로 생성).
  주의: ANTHROPIC_API_KEY가 설정돼 있으면 프로필보다 우선하므로, 로그인 계정을
  쓰려면 해당 환경변수를 비워야 함.
- **Batch API 사용(요금 50%)** — 대신 즉시 응답이 아니므로 명령이 셋으로 나뉨:
  `submit`(제출) / `status`(진행 확인) / `fetch`(엑셀 회수).
  제출과 회수가 별개 실행이라, 그 사이 상태는 `.batch_jobs/<batch_id>.json`에 보관.
  이 파일에는 custom_id(img-0001 …) ↔ 원본파일명 매핑과 채널/카테고리/조사일자가 들어감
  (배치 결과는 순서가 보장되지 않고 custom_id로만 식별되므로 이 매핑이 필수).
  회수 완료 표시는 엑셀 저장에 성공한 뒤에만 기록 → 저장 실패 시 fetch 재실행으로 복구 가능.
- 배치는 24시간 내 미완료 시 만료(요금 미청구). 개별 요청 실패는 배치 전체를
  실패시키지 않으며, 실패·만료 사유는 해당 행의 비고란에 남음.
- 출력 엑셀은 회수할 때마다 기존 파일에 새 행을 이어붙임 (누적 데이터베이스처럼 사용).
  간헐적으로 실행되는 툴이라 세션 간 기억이 없으므로, 상태는 엑셀 파일 자체에 저장됨.
- 컬럼: 조사일자/채널/카테고리/원본파일명/브랜드명/제품명/판매가(원)/용량_원문/
  구성_원문/총용량/단위/단위당가격(원)/단가기준/쿠팡표기단가/단가검증/제품형태/제품역할/
  순위/순위_원문/리뷰수/월구매자수(명)/구매자수_원문/추정월매출(원)/형태_판단근거/
  상품URL/검색링크/비고
- **시장 지표**: 카테고리 순위, 리뷰수, 월구매자수를 함께 수집. 가격만으로는 시장
  위치를 볼 수 없어 추가함. 순위·구매자수는 원문 문구를 그대로 받아두고 파이썬이
  숫자를 뽑음('2만명' -> 20000 등 한글 단위 환산 포함).
- **'구매했어요' vs '만족했어요' 구분이 필수.** 쿠팡은 같은 자리에 두 문구를 번갈아
  보여주는데 '만족'은 구매자수가 아님. 코드가 문구에 '구매'가 있을 때만 숫자로
  인정하며, 아니면 월구매자수와 추정월매출을 비움(원문은 컬럼에 남겨 사람이 확인 가능).
  이 판정을 AI에게 맡기지 않는 이유는 매출 추정의 근거가 되는 값이기 때문.
- **추정월매출 = 월구매자수 x 판매가 x REVENUE_OPTION_MULTIPLIER(기본 2)**.
  한 상품 페이지에 여러 옵션이 묶여 있고 구매자수는 페이지 단위라 배수를 곱함.
  구매자수가 '이상'으로 끝나는 하한값이고 배수도 어림이므로 절대액으로 쓰지 말고
  제품 간 규모 비교용으로만 볼 것. 배수를 바꾸려면 해당 상수를 수정하거나
  엑셀에서 다시 곱하면 됨(구성 값이 모두 컬럼에 있음).
- **형태(겉모습)와 역할(본품/리필)은 반드시 별도 칸으로 둘 것.** 실제 쿠팡 데이터에서
  "말통 형태의 리필 제품"이 나와, 한 칸으로는 둘 중 하나를 잃어버림을 확인했음.
  `product_form`=용기/파우치/말통/기타, `product_role`=본품/리필/불명.
  역할은 제품명에 '본품'/'리필'로 적혀 있는 경우가 많아 시각 판단보다 정확함.
  같은 이유로 '세트'는 형태에서 제외함 — 수량은 `구성_원문`이 담당하는 별개 축임.
- **단위는 용량(ml/g)과 개수(개) 두 갈래.** 캡슐세제처럼 개수로 파는 카테고리가 있어
  `parse_capacity`가 '26개입' -> (26, '개')도 처리함. 기준은 `unit_price_basis`가 정함:
  액체는 100ml/100g당, 개수 제품은 1개당. 엑셀의 `단가기준` 컬럼에 어느 기준인지 표기됨.
  제품명이 '...,26개입, 1개' 형태이면 앞이 capacity_text(팩 크기), 뒤가
  composition_text(묶음 수량)임 — 액체의 '500ml, 4개'와 같은 구조.
- **단가 검산**: 쿠팡은 '(100ml당 1,190원)'을 화면에 이미 표시함. 이 표기를
  `unit_price_text`에 원문 그대로 읽어두고, 파이썬이 100 기준으로 환산해 우리 계산과
  대조함(`단가검증` 컬럼). 용량이나 가격을 잘못 읽으면 여기서 불일치로 드러나므로,
  추가 비용 없이 정확도를 검증할 수 있음. 읽기는 AI / 환산·비교는 코드 원칙 유지.

### `analyze_details.py` (4단계, 도구 구현 완료 / 데이터 수집 대기)
- 명령: `targets`(수집 대상 선정·지시문 생성) / `inventory`(캡처 파일 점검·번호 매기기)
  / `build`(검증·집계·엑셀).
- **`targets`는 `문서생성/견적요청서_데이터.json`(생산 스펙)을 읽어 대상을 고른다.**
  저가군을 카테고리 전체가 아니라 **우리가 만들려는 형태·규격군 안에서** 고르는 것이 핵심.
  형태가 다르면 가격 구조가 달라 경쟁 상대가 아니다(섬유탈취제를 용기로 만드는데
  파우치 최저가의 소구점을 참고하면 엉뚱한 결론이 나옴). 실제로 형태 제약 없이 돌렸을 때
  살균소독제는 업소용 20L만 2개 뽑히고 가정용 4L 경쟁자가 빠졌음.
  스펙 파일이 없으면 카테고리 전체에서 고르되 그 사실을 출력에 표시한다.
- 두 무리를 함께 고른다: `경쟁`(우리 스펙과 같은 형태의 최저가) + `고가 상위권`
  (10위 이내 중 단가 최고). 각각 "싸게 파는 곳은 뭘로 설득하나" /
  "비싼데도 왜 팔리나"에 답한다.
- 지시문의 제품 목록에는 **브랜드·규격·조사시점 판매가**를 함께 넣는다. 쿠팡 제품명에
  브랜드가 빠진 경우가 많아(리퀴드·퍼플리·허니맘) 검색 결과에서 엉뚱한 상품을 열 수 있고,
  같은 이름의 다른 용량 옵션을 열기도 쉽다. 가격은 변동하므로 '조사 시점' 값임을 명시하고
  브랜드·규격으로 확인하게 한다.
- **틀은 고정, 내용은 자유**가 설계 원칙. USP는 문장이라 자유 서술하고 싶어지지만
  그러면 제품 간 집계가 안 됨. 그래서 `kind`(유형)는 정해진 값 중 선택하게 하고,
  `claim`(소구점)은 자유 문장, `evidence`는 **페이지 원문 그대로** 옮기게 함.
  evidence를 원문으로 못박은 이유는 지어내기 방지 — 썸네일 쪽 단가검증과 같은 역할.
- `emphasis`(강조도)와 `position`(상단/중단/하단)을 함께 받음. 판매자가 위에 크게
  배치한 것일수록 핵심 소구점이라는 전제.
- `--thumbnails`로 2단계 엑셀을 주면 제품명 기준으로 순위·단가·리뷰수를 붙임.
  이게 이 도구의 핵심 가치: **"비싼 제품은 뭘 내세우나"**를 볼 수 있게 됨.
- 출력 시트: 유형별집계 / 제품별요약 / USP전체.
- PDF 쪽수 확인(pypdf)은 부가기능. 미설치·설치 깨짐에도 전체 작업이 되도록
  모듈 로드 시 한 번만 시도하고 실패하면 조용히 넘어감(파일마다 시도하면 오류가 반복됨).
  쪽수가 1~2쪽이면 "스크롤 전에 저장" 의심 대상으로 경고함.

### 상품 URL 확보
- **현재 150건 전부 `상품URL`이 비어 있음(0/150).** 실제 상품 주소를 받아온 적이 없다.
  URL 수집 시도는 브라우저 확장 지시문 단계에서 끊겼고 그대로 멈춰 있음.
  `검색링크`(제품명 기반 쿠팡 검색 주소)는 150/150 채워져 있음.
- 앱 화면 캡처에는 주소가 찍히지 않아 실제 상품 URL을 알 수 없음. **추측해서 만들지 말 것**
  (엉뚱한 상품으로 연결되어 없느니만 못함). `product_url`은 그 경우 null.
- 대신 `검색링크` 컬럼에 제품명 기반 쿠팡 검색 주소를 자동 생성함. 클릭 한 번으로 찾아감.
  제품명에 브랜드가 이미 들어 있는 경우가 많아 중복을 걸러서 질의를 만듦.
- 브라우저(Claude in Chrome 등)에서 수집할 때는 주소창 URL을 `product_url`에 담을 것.
  그러면 다음 회차부터 검색 없이 바로 열 수 있음.
- `analyze_thumbnails.py urls` 가 브라우저에 붙여넣을 URL 수집 지시문을 생성함.
  `--select 카테고리:순위,순위` 로 여러 카테고리에서 골라 뽑을 수 있음.
  제품명을 사람이 옮겨 적다 빠뜨리는 것을 막는 것이 목적이므로, 지시문에 목록을
  **전부 채워서** 내보냄(자리표시자를 남기면 사용자가 그대로 붙여넣게 됨).
- `--pace N`(기본 4)로 묶음 처리 지시를 넣음. 목적은 속도 조절보다 **중간 결과 보존**임.
  한 번에 몰아서 시키면 중단됐을 때 그때까지 한 것이 통째로 날아가므로, 묶음마다
  결과를 먼저 출력하게 함. 검색 사이에 쉬라는 지시도 포함.
  목록이 pace보다 짧으면 불필요한 지시를 넣지 않음.

### 수집 범위를 정하는 기준
- **URL 수집도 넓게, USP 추출도 전수조사.**
- URL은 한 번 받아두면 계속 쓰는 자산이라 카테고리 전체(25개씩)를 받아둘 만함.
  다음 회차부터 검색 단계가 통째로 사라짐.
- **USP는 전수조사가 기본이다.** 처음에는 "질문에 필요한 제품만"으로 좁혔는데
  (150 -> 13) 이는 잘못된 판단이었음. USP는 가격·판매량과 무관하게 제품마다
  다른 소구점이 존재하므로, **어느 제품에 쓸모 있는 인사이트가 있는지 미리 알 수 없다.**
  저가/고가로 고르면 그 축과 무관한 소구점을 통째로 놓친다.
  (예: 순위 24위 클로시딘의 '반려동물 피부 소독 겸용'은 가격·순위와 아무 상관이 없지만
  카테고리 확장을 생각하면 가장 값진 정보일 수 있음)
- 다만 방식이 확정되기 전에는 작은 묶음으로 **테스트부터** 한다. 브라우저가 한 번에
  몇 개를 안정적으로 처리하는지, 검색으로 맞는 상품을 여는지, evidence를 원문대로
  가져오는지를 먼저 확인한 뒤 전수조사로 넘어간다.
  `targets`의 표본 선정 모드(기본)는 이 테스트용으로 남겨둔 것이고,
  실제 수집은 `--all`이다.
- 150개를 여러 묶음에 나눠 수집하므로 **이어하기가 필수**:
  `targets --all --batch 10 --done ../data/usp` 를 반복하면 남은 것만 나온다.
  진행 상황은 별도 상태 파일이 아니라 **받은 결과 자체**에서 읽는다(어긋날 일이 없음).
- **브라우저에서 받은 원본 JSON은 `data/usp/`에 저장하고 커밋한다.** 엑셀은 gitignore
  대상이고 작업 환경(컨테이너)은 일회용이라, 여러 세션에 걸쳐 수집하려면 원본이
  저장소에 남아야 한다. `build --input ../data/usp` 로 폴더를 통째로 읽으면 엑셀이
  언제든 재생성된다. 카테고리는 항목 ID에서 읽으므로 --category 불필요.
- **사람에게 줄 파일은 `--prompt-only`로 만든다.** 작업용 진행 요약이 같이 들어가면
  "어디서부터 복사하지?"가 된다. 실제로 그렇게 줬다가 사용자가 혼란스러워했음.
- 사람이 하는 일은 **붙여넣기와 결과 전달 두 가지뿐**이다. 터미널 명령은 Claude가
  실행한다. 명령어를 사용자에게 안내하듯 적지 말 것 — 사용자는 개발 경험이 많지 않고,
  이 프로젝트의 실행 주체는 Claude다.
- 항목 식별자는 `카테고리-파일번호`(예: `세탁세제-09`). 제품명으로는 안 됨 —
  같은 카테고리에 제품명이 똑같고 가격만 다른 옵션이 실제로 있다
  (스너글 섬유탈취제, 프릴 주방세제). 추출 원본 파일명은 카테고리별로 고유하므로
  원본 캡처까지 거슬러 갈 수도 있다.
  브라우저가 ID를 다르게 적으면 `targets`가 '대상에 없는 ID'로 알려주고, 그 항목은
  남은 목록에 그대로 둔다(조용히 건너뛰지 않음).
- **`build`는 기존 엑셀에 이어붙인다.** 덮어쓰면 앞 묶음이 통째로 날아가고,
  진행 상황을 이 엑셀에서 읽기 때문에 "일부만 수집된 결과를 전부인 줄 알고 받는"
  최악의 실패가 된다. 같은 ID를 다시 넣으면 새 결과로 교체한다(재수집 = 수정 의도).

### 입력·폴더 구조 정비 (2026-09-30, v1.2.0)
- 실전 3차: 2건 모두 "성공"이나 001 은 2장, 002 는 9장. 사용자 표현으로는
  **"한 개는 되는데 한 개는 안 되네"**. 요청은 둘이었다 — 입력 구분자, 폴더 이름.
- **입력 파싱이 취약했다.** 기존 정규식 `/^(\S+)[\s,]+(https?:\/\/\S+)$/` 하나로
  "이름 주소"를 한 번에 맞추려 했다. 쿠팡 주소는
  `?searchId=...&clickEventId=...&q=%EB%9D%BC...&searchRank=0` 처럼 길어서
  붙여넣을 때 두 줄로 접힌다. 그러면 **잘린 주소가 조용히 목록에 들어가**
  엉뚱한 페이지를 긁고도 "성공"으로 끝난다.
- 고친 방식:
  (1) 줄에서 `http` 가 처음 나오는 자리를 찾아 앞=이름 / 뒤=주소로 나눈다.
      → 구분자가 `|` 든 쉼표든 탭이든 공백이든 다 통한다. **권장은 `|`**.
  (2) 주소에서 딜번호 `/v[pm]/products/(\d+)` 를 반드시 뽑는다.
      **못 뽑으면 받지 않고** 빨간 칸으로 몇 번째 줄이 왜 안 되는지 보여준다.
      background 의 `start` 에서도 한 번 더 막는다(패널을 우회해도 안 들어간다).
  (3) `cleanUrl()` 로 추적 꼬리표(searchId/clickEventId/searchRank/q/…)를 떼고
      `itemId`, `vendorItemId` 만 남긴다. 이 둘은 '어느 옵션'이라 상세가 달라진다.
      덤으로 같은 상품을 다른 검색에서 두 번 넣어도 같은 주소로 모여 중복이 사라진다.
  (4) **시작 전에 미리보기 표**를 띄운다(항목 / 딜번호 / 저장될 폴더).
      이것이 핵심 안전장치다. '조용한 실패'를 눈에 보이는 실패로 바꾼다.
- **폴더 이름을 딜번호로 바꿨다.** `001`, `002` 는 **그날 목록의 순서**일 뿐이라
  다음에 순서를 바꿔 돌리면 어제의 `001` 에 오늘의 다른 제품이 덮어써진다.
  딜번호는 상품마다 하나뿐이어서 이런 사고가 없다. 모드 3개:
  `id`(기본, 딜번호) / `id_title`(딜번호_제품명) / `label`(내가 붙인 이름).
  이름을 안 붙이면 **항목 id 자체도 딜번호**가 되어 이어하기가 상품 단위로 맞는다.
- **덮어쓸 때 예전 파일을 지운다(`clearOldFiles`).** 지난번 9장 → 이번 2장이면
  `003~009` 가 남아 폴더만 보고는 몇 장인지 알 수 없다. `downloads.search` 로
  그 폴더의 `001.jpg` 꼴 파일만 골라 `removeFile`. 범위를 좁힌 이유는 남의 파일을
  지우지 않기 위해서다.
- 검증: 실제 크롬에 확장을 올려(Playwright `--load-assets`/persistent context)
  서비스워커 기동, 미리보기 표, 잘린 주소 경고, 폴더 모드 전환, results.html 까지
  **JS 오류 0건** 확인. 파싱 6종·폴더명 6종은 node 단위 시험.
- **남은 진짜 의문: 001 의 2장이 파싱 실패인지 상세가 원래 짧은 것인지 아직 모른다.**
  `수집기록.json` 을 받아야 갈린다. 이제 기록에 `productId`, `folder`, 딜번호 로그가
  남으므로 다음 회차에는 구분된다. **추측으로 닫지 말 것.**

- 사용자: "우선 돌릴 제품들의 URL을 취합해야하는데, 여기서 또 병목임."
- 업로드된 엑셀 2종을 대조했다. **11개 카테고리 275개짜리가 최신본이고
  6개 150개짜리를 완전히 포함한다**(148/148 일치, 121개 추가).
  11개 파일에는 `쿠팡URL` 열이 이미 있고 **121개가 채워져 있다.**
  비어 있는 것은 **154개**(원래 6개 카테고리 150 + 욕실세정제 2 + 향기지속제 2).
- **썸네일 이미지만으로 URL을 찾아줄 수는 없다.** 여기서는 쿠팡에 접속이 안 된다(403).
  그리고 **주소를 지어내는 것은 절대 안 된다.** 대신 사용자 브라우저에서
  검색하게 했다 — 이미지 수집과 똑같은 원리다.
- 만든 것:
  - `문서생성/검색목록_생성.py` : 엑셀 → `검색목록.json` (id/제품명/**기대가격**/용량)
  - `coupang_extension/search.js` : 검색 결과에서 후보 8개까지 추출
  - background `scoreCandidate()` : 이름 일치도 + **가격 대조**로 확실/애매/못찾음
  - `문서생성/검색결과_병합.py` : 확실만 엑셀에 반영, 애매는 후보째로 따로 뺌
- **설계의 핵심은 '검색 1등을 집지 않는 것'이다.** 같은 이름 다른 용량이 흔하다.
  모의시험에서 정답(2.1L 14,650원)과 함정(4.2L 27,800원)은 **이름 일치도가 둘 다
  100%** 였다. 가른 것은 가격뿐이다(0% vs 90%). 이름만 봤으면 틀렸다.
  → **기대가격을 목록에 함께 실은 것이 이 기능을 성립시킨다.**
- 후보는 판정과 무관하게 5개까지 기록에 남긴다. 채점이 틀려도 원자료가 남아
  여기서 다시 판정할 수 있다. **조용히 확정하지 않는다.**
- search.js 는 **클래스 이름에 기대지 않는다.** `a[href*="/vp/products/"]` 로 찾아
  올라가며 칸을 잡는다. 클래스는 배포마다 바뀌지만 주소 구조는 안 바뀐다.
- 검증: 모의 검색 3종(정답+함정3 / 결과없음 / 차단) 통과. 실제 크롬에 확장을
  올려 탭 전환·목록 파싱·잘못된 입력 처리·결과 페이지까지 JS 오류 0건.
  병합 스크립트는 가짜 결과로 확실/애매/못찾음 분기까지 확인.

### 같은 실수를 두 번 했다 — 검색도 늦게 그려진다 (2026-09-30, v1.4.1)
- 1차 실전(2건): 둘 다 `못찾음`. 기록이 원인을 바로 말해 줬다.
  ```
  제목: 쿠팡!            ← 검색어가 안 들어간 제목 = 아직 결과가 안 그려짐
  상품 링크 0개 발견
  ```
- **바로 앞에서 고친 것과 똑같은 버그다.** 상세 영역이 나중에 그려지는 것처럼
  검색 결과도 나중에 그려진다. `waitForLoad`(status=complete)는 뼈대가 온 시점이지
  내용이 온 시점이 아니다. content.js 에는 `waitForDetail` 을 넣어 놓고
  **search.js 에는 그 교훈을 옮기지 않았다.**
- **교훈: 한 곳에서 고친 버그는 같은 모양의 다른 곳도 함께 점검해야 한다.**
  "페이지가 로딩 완료되면 내용이 다 있다"는 가정을 깔고 쓴 코드가 또 없는지
  다음부터는 고칠 때 같이 훑는다.
- 고친 것:
  (1) `waitForResults()` — 상품 링크 수가 늘다가 멈출 때까지 대기(최소 3초,
      최대 16초). 중간에 안 늘면 한 번 훑어 지연 로딩을 깨운다.
  (2) 차단 검사를 **기다리기 전과 후 두 번** 한다. 늦게 뜨는 차단 화면도 잡는다.
  (3) PC 검색이 비면 **모바일 검색(m.coupang.com/nm/search)** 으로 재시도.
  (4) **`못찾음`과 `화면못읽음`을 분리했다.** '결과가 없다'와 '못 읽었다'는 전혀
      다른 문제고, 섞어 놓으면 엉뚱한 곳을 고치게 된다. 못 읽었을 때는 전체 링크
      수·본문 글자수·'결과없음' 문구 유무·링크 예시를 기록에 남긴다.
- 검증: **실전 증상을 그대로 재현한 모의 페이지**(제목 "쿠팡!", 4초 뒤 결과 렌더)에서
  구판 0개 / 신판 4개 → 정답 `확실`. 검색 모의 4종 전부 통과.
  실제 크롬 확장 적재도 JS 오류 0건.

### 쿠팡이 검색 주소를 막는다 — 순위 페이지로 우회 (2026-09-30, v1.5.0)
- v1.4.1 로 기다리게 했는데도 실패. 그런데 **이번엔 진단값이 답을 줬다.**
  ```
  bodyHead: "요청하신 페이지의 사용권한이 없습니다. ... Ref: 1C93A0DD_..."
  진단 — 전체 링크 3개 / 본문 글자수 249 / '결과없음' 문구 없음
  ```
- **기다림 문제가 아니었다. `/np/search` 자체가 거부된다.**
  `/vp/products/...` 는 멀쩡히 열린다(이미지 수집이 그 증거다). 검색만 막는다.
  모바일 검색(`m.coupang.com/nm/search`)도 `www.coupang.com/np/search` 로
  리다이렉트되어 같은 거부 화면이 떴다.
- **`화면못읽음`을 따로 만들어 둔 덕에 한 번에 갈렸다.** `못찾음` 하나로 뭉뚱그렸으면
  또 검색어나 대기시간을 고치고 있었을 것이다. **실패를 세분해 두는 값이 이것이다.**
- 우회하지 않고 **다른 길로 갔다.** 지문 위장은 하지 않는다는 원칙은 그대로다.
  애초에 이 목록은 **카테고리 구매 순위 1~25위**에서 뽑은 것이다
  (`순위_원문` = "액체세제 구매 1위"). 순위 페이지 한 장에 25개가 다 있다.
  → `readCurrentList()`: **사용자가 직접 연 화면**을 읽어 대조한다.
    주소를 대신 두드리지 않으므로 막힐 일이 없다. 검색 154번 → 페이지 6장.
- 엑셀 카테고리 ↔ 쿠팡 순위 목록 이름 (실측, `순위_원문`에서 추출):
  세탁세제→**액체세제** / 캡슐세제→**캡슐세제** / 섬유유연제→**액체섬유유연제** /
  섬유탈취제→**섬유탈취제** / 주방세제→**일반주방세제** / 살균소독제→**살균소독제**
  (상품 페이지의 "구매 1위 ○○ 순위 >" 를 누르면 바로 그 목록이다)
- 매칭은 검색과 같은 `scoreCandidate()` 를 쓴다. 다만 한 딜번호가 두 항목에
  겹쳐 붙지 않도록 확정된 것은 후보에서 뺀다.
- 검증: **실제 검색목록의 세탁세제 25개**로 모의 순위 페이지를 만들고
  광고 2개 + 함정 1개(같은 1위 제품의 4.2L 2개짜리)를 섞었다.
  → **확실 25/25, 함정 오인 0, 딜번호 중복 배정 0.**
- search.js 의 MAX 를 8 → 60 으로 올렸다. 랭킹은 25위까지 봐야 한다.

### 확인하지 않은 것을 확인한 것처럼 썼다 (2026-09-30, v1.5.1)
- v1.5.0 안내에 **"상품 페이지의 '구매 1위 ○○ 순위 >' 를 누르면 바로 그 목록"**

  그대로 하다가 막히고, 그 시간은 온전히 사용자가 버린다.

### 파일을 줬으면 파일로 받아야 한다 (2026-10-01, v1.6.1)
- 사용자: **"검색목록json파일을 어디에 붙여넣으라는거야?"** (확장 폴더 스크린샷과 함께)
- 내가 `검색목록.json` 을 파일로 보내 놓고, 쓰는 법은 **"내용을 복사해서
  입력칸에 붙여넣으세요"** 라고 했다. 그래서 **파일을 확장 폴더에 넣는 것으로**
  오해할 여지를 만들었다. 파일을 받았으면 파일로 고르게 하는 게 맞다.
- 고친 것: 패널에 **`📂 검색목록.json 파일 선택`** 버튼(`<input type=file>`).
  붙여넣기 칸은 `직접 붙여넣기` 토글 뒤로 숨겼다. 오류 문구도 파일 기준으로 바꿨다.
  문서에 **"확장 폴더에는 아무것도 넣지 마세요"** 를 명시했다.
- 스크린샷에서 확인된 것: 압축을 풀어 `coupang_extension/coupang_extension` 으로
  한 겹 더 들어간 상태였다. **manifest.json 이 있는 폴더를 가리키면 되므로 문제없다.**
  `설치방법.md` 는 한글 파일명이라 탐색기 목록 아래쪽에 있어 화면에 안 보였을 뿐
  실제로는 들어 있다(19KB).
- **교훈: 산출물의 '형태'와 '쓰는 법'을 맞춘다.** 파일로 주고 복사·붙여넣기를
  시키면 그 사이에서 사용자가 길을 잃는다. 앞의 두 교훈(모르는 걸 말하지 않기,
  아는 걸 말하기)에 이어 **'준 것과 시키는 것을 어긋나게 하지 않기'** 를 더한다.

### 찾아야 할 파일이 하나라도 있으면 걸림돌이다 (2026-10-01, v1.7.0)
- 사용자: **"이 파일이 폴더에는 없는데?"**
- `검색목록.json` 을 채팅으로 따로 보내 놓고 확장에서 고르게 했다. 사용자는
  확장 폴더를 열어 거기서 찾았다. **당연한 행동이다** — 확장 얘기를 하는 중에
  파일 얘기를 했으니 확장 폴더에서 찾는 게 자연스럽다.
- v1.6.1 에서 파일 선택 버튼을 단 것으로는 부족했다. **고르게 하는 것 자체가
  문제였다.** 목록을 확장에 함께 넣고 패널이 열릴 때 바로 읽는다
  (`fetch(chrome.runtime.getURL("search_list.json"))`).
  **이제 패널을 열면 표가 떠 있다. 사용자가 할 일이 없다.**
- 파일 이름은 `search_list.json` (영문). 한글 파일명이 경로에서 깨진 전례가 있다
  (.bat CP949 건). 확장 내부 경로에는 영문만 쓴다.
- 파일 고르기와 붙여넣기는 남겨 뒀다. 목록이 바뀌면 새 확장을 보내는 게 기본이지만,
  급할 때 파일로 넣을 길은 있어야 한다.
- **교훈: 사용자에게 남기는 '준비 단계'의 개수를 센다.** 단계마다 길을 잃을 수 있다.
  파일 받기 → 저장 → 찾기 → 고르기 = 네 단계였고, 네 번 다 틀릴 수 있었다.
  지금은 0단계다. 세 번 연속 같은 자리에서 막혔다는 건

### 변하는 값으로 같음을 판정하고 있었다 (2026-10-01, v1.8.0)
- 실전: 순위 페이지 읽기로 **154개 중 120개 확정.** 남은 34개를 두고 사용자가
  정확한 질문을 했다. **"가격은 변할 가능성이 높은 구분자라 혹시 모든 조건이
  다 맞아야 매칭이 되는건지 확인좀."**
- 맞는 지적이었다. 당시 규칙:
  ```js
  if (nameScore >= 0.6 && priceGap <= 0.03) 확실
  else if (nameScore >= 0.85 && (priceGap === null || priceGap <= 0.15)) 확실
  ```
  **가격이 15% 넘게 움직이면 이름이 100%여도 '확실'이 못 된다.** 쿠팡은 할인이
  수시로 바뀌므로 15%는 자주 넘는다. 남은 34개의 상당수가 이것으로 보인다.
- **게다가 `sizeOk` 를 계산해 놓고 판정에 쓰지 않았다.** 반환값에만 실어 보냈다.
  변하지 않는 증거를 손에 쥐고 변하는 증거로 판정한 셈이다.
- 바꾼 원칙: **규격(용량·구성)이 1차 증거, 가격은 보조 증거.**
  용량·구성은 쿠팡 제목에 그대로 찍히고("…코튼향, 2.1L, 1개") 시간이 지나도 안 변한다.
  - `hasSpec()` 은 단순 includes 가 아니다. "3L"이 "13L"에, "1개"가 "21개"에
    걸리지 않도록 앞뒤가 숫자가 아닌지까지 본다. 경계 시험 8종 통과.
  - 용량이 다르면 이름이 100%여도 **확실 아님**(애매로 내림).
  - 용량·구성이 맞으면 **가격이 얼마가 변했든 확실.**
- **시험 중에 진짜 오탐을 하나 잡았다.** 규격 경로 기준을 0.6 으로 뒀더니
  "피지 모락셀라 냄새제거 **세탁세제** 코튼향" 과
  "피지 모락셀라 냄새제거 **섬유유연제** 코튼향" 이 낱말 5개 중 4개(0.8)가 같고
  용량·구성도 같아(둘 다 2.1L 1개) **확실로 붙었다.** 0.85 로 올려 막았다.
  → **한 낱말 차이가 곧 다른 제품인 경우가 있다.** 점수만 보면 못 본다.
- 판정 사유(`why`)를 기록에 남기고 결과 표에 칸을 추가했다. 왜 확정/보류했는지
  사람이 읽을 수 있어야 한다.
- 패널에 **△ 애매** 개수를 카테고리별로 표시한다. 전에는 '남은 N개'에 섞여 있어
  "후보는 찾았는데 보류된 것"과 "아예 못 찾은 것"이 구분되지 않았다.
- 시험: 가격 변동 4종(0%/-20%/+50%/못읽음) 전부 확실, 함정 3종(다른 용량·다른 구성·
  다른 제품) 전부 보류, 순위 페이지 25/25, 검색 모의 4종 회귀 통과.
- **교훈: 같음을 판정할 때는 '변하지 않는 값'을 1차 증거로 둔다.**
  가격·순위·리뷰수는 변한다. 용량·구성·딜번호는 안 변한다.

### 수집 경로 변경 (2026-09-28): Playwright -> 크롬 확장
- **Playwright 자동화는 쿠팡이 차단했다.** probe 실행 시 검색 페이지에서 차단 확인.

  접근 제한을 사람인 척 속여 넘는 것이고, 쿠팡 약관도 자동 수집을 금지한다.
- 대신 `../coupang_extension/` 에 **크롬 확장**을 만들었다. 사용자의 실제 브라우저에서
  동작하므로 위장이 필요 없다. 상품 URL을 넣으면 탭을 열어 '더보기'를 누르고
  상세 이미지 주소를 모아 내려받는다.
- **가져오는 것은 상세페이지 이미지뿐이다. 상품 썸네일이 아니다.**
  `#productDetail` 등 상세 영역 '안쪽'만 본다. 상세 영역을 못 찾아 페이지 전체를

  (EXCLUDE_SELECTORS). 결과에 `scope`/`fallback`을 남겨 어디서 긁었는지 알 수 있다.
- **PDF가 아니라 이미지로 받는다.** 분석 대상이 결국 이미지이고, 이미지 주소는
  지연 로딩 상태에서도 data-src 에 이미 들어 있어 끝까지 스크롤할 필요가 없다.
- 셀렉터는 여기서도 **글자 기준**(EXPAND_TEXTS). 아이콘·스페이서·svg 는 크기로 거른다.

  상세 영역 탐지 → 이미지 3장 수집, 아이콘/gif/svg 제외 확인. 차단 화면과
  이미지 없음 화면의 감지도 확인. **쿠팡 실환경은 미검증.**
- 수집 기록(수집기록.json)에 항목별 status/사유/이미지 주소가 남으므로,
  실패해도 무엇 때문인지 판단할 수 있다.
- 제품명만으로도 소구점 단서가 77%(115/150) 나오지만, **효소 종수·더마·불검출·

  (개발 환경 검증 완료: 13,200px -> PDF 13쪽 + 이미지 5장)
- **셀렉터는 CSS 클래스가 아니라 버튼에 적힌 글자로 찾는다.** 클래스명은 배포마다

- 차단 감지 / 연속 3회 실패 시 중단 / 상품당 20~40초 무작위 대기.

- **Claude in Chrome(브라우저 확장)이 쿠팡에서 동작하는지는 아직 검증되지 않았음.**
  (2026-09-28 기준) 사용자의 브라우저·로그인으로 도니 403이 안 날 것이라고 추측했고,
  한때 이 파일에 그것을 사실처럼 적어뒀으나 **실제로 결과가 나온 적이 없다.**
  시도는 지시문 자리표시자 문제에서 끊겼고, 막혔다는 확인도 없다. 즉 미검증.
  다음에 이 경로를 쓰려면 **제품 1개로 먼저 확인할 것.** 되면 그때 확장해도 늦지 않다.
  추측을 메모리에 사실로 적으면 그 뒤 모든 계획이 그 위에 쌓인다 — 실제로 그렇게 됐다.
  검증되면 다음 이점이 있음: 캡처가 불필요하고, 별개 세션이라 결과가 자동으로
  넘어오지 않으므로 **스키마를 계약서로 삼음**:
  `analyze_details.py prompt`가 스키마에서 지시문을 생성 -> 브라우저에서 JSON 출력 ->
  여기 붙여넣고 `build`가 검증. 형식이 어긋나면 그 자리에서 걸러짐.
  지시문을 코드로 생성하는 이유는 스키마와 어긋나지 않게 하기 위함(손으로 적어두면
  스키마를 고쳤을 때 둘이 따로 놀고, 받은 결과가 전부 튕김).
- USP는 전수조사가 기본이므로 캡처 방식으로는 부담이 너무 크다. 브라우저 확장으로
  묶음을 나눠 진행하는 것이 사실상 유일한 현실적 경로다(위 '수집 범위' 항목 참고).

### 5단계 산출물: 생산 견적 요청서 (`../문서생성/`)
- `견적요청서_데이터_생성.py`가 `data/extracted`에서 숫자를 계산해 JSON으로 내보내고,
  `견적요청서_생성.js`(docx-js)가 그 JSON으로 문서를 만든다. 숫자를 손으로 적지 않는
  이유는 판매가·원가·단가가 서로 맞물려 있어 한 곳만 고치면 반드시 어긋나기 때문.
- **스펙 도출은 '형태'(용기/파우치/말통)로만 나눈다. 본품/리필로 나누지 말 것.**
  본품·리필은 브랜드가 자기 라인업 안에서 붙이는 이름이라, 인지도가 다른 브랜드끼리
  1:1로 비교하면 "리필을 본품보다 비싸게 만들자"는 결론이 나온다. 실제로 그렇게 나왔고
  사용자가 잡아냈음. 형태는 브랜드와 무관한 사실이라 비교 기준으로 쓸 수 있다.
  `제품역할` 컬럼 자체는 시장 관찰 사실이므로 엑셀에 남기되, 스펙 계산에는 쓰지 않는다.
- 실제 데이터에서 확인된 반례: 섬유유연제 말통 5건은 전부 **본품**이고 리필은 파우치 7건.
  캡슐세제는 25건 전부 본품이며 리필이라는 구분이 아예 없다(파우치 23 / 용기 2).
  "말통=리필"은 상식이지 데이터가 아님.
- **카테고리당 단위당가격이 가장 싼 형태 1종만 생산한다.** 형태별로 다 만들면 비싼 형태는
  가성비 제품으로 성립하지 않고, 용량이 커질수록 실현 불가능한 원가가 나온다.
  나머지 형태는 기능을 차별화한 확장 품목으로 미뤄둔다(문서 5장 '확장 후보').
- 형태별 최저 단가가 어디인지는 카테고리마다 다름: 세탁세제·섬유유연제·섬유탈취제는 용기,
  주방세제·살균소독제는 말통, 캡슐세제는 파우치.
- 가격대 최저가 산정: 그 형태에서 **실제로 판매 중인 최저가**의 −5%.
  **이상치 자동 제외(다음 값보다 1.5배 이상 싸면 버림) 규칙은 폐기했다.**
  처음엔 섬유유연제 10L 6,890원이 시장에 없는 가격처럼 보여 규칙을 넣었는데,
  확인해보니 '리퀴드'라는 실재 브랜드였고 같은 브랜드가 세탁세제 10L도 팔고 있어
  가격이 서로 일관됐다. 그 형태·그 가격에 파는 곳이 있으면 그것이 시장 가격이다.
  브랜드가 미상으로 나오면 버리지 말고 **추출 원본의 notes를 먼저 확인할 것**
  (이 건도 notes에 '라벨은 Laundry LiQiD'가 적혀 있었다).
  대신 최저가와 그 다음 값의 격차(gapRatio)가 1.5배 이상이면 문서에 그 사실을
  밝힌다 — 목표가가 시장 대다수보다 한참 아래라는 뜻이므로 공장이 알아야 한다.
- **무게(g/kg)와 부피(ml/L)는 같은 선에서 비교한다.** 물리적으로는 다른 단위지만
  생활용품 시장은 둘을 병행 표기하고 소비자도 100g당·100ml당을 나란히 놓고 본다.
  시장의 비교 방식을 따르는 것이 목적. 단가기준 라벨은 `100ml·100g당`으로 표기.
  개수(캡슐세제 1개당)는 성질이 달라 여전히 별도 무리다.
  (전체 150건 중 무게 표기는 주방세제 트리오 14kg 1건뿐)
- 단가 기준이 다른 행은 밴드 계산에서 제외한다(주방세제 말통의 트리오 14kg는 100g당).

### 향후 아이디어: 대시보드 (미착수)
- 사용자 요청: 로컬 폴더를 대시보드에서 열어(업로드해) 분석을 돌리고 결과를 보는 형태.
- 착수 전 확인 필요: 브라우저는 보안상 로컬 경로를 직접 읽지 못함. 선택지는
  (a) 폴더 선택 UI로 파일을 읽어 올리는 웹앱(로컬 서버 + 브라우저 파일 선택),
  (b) 로컬에서 도는 데스크톱/로컬웹 앱(경로를 그대로 다룰 수 있음).
  현재 도구가 `ant` CLI와 로컬 상태파일(.batch_jobs)에 의존하므로 (b)가 더 자연스러움.
- 대시보드가 생기면 status/fetch를 사람이 명령으로 치지 않아도 되므로,
  배치 진행 상황 표시와 결과 열람이 주된 가치가 됨.

## 지켜야 할 제약/원칙

- 회사명(클라코리아/타이드웍스/담다다담/엘든코리아 등 운영주체명)은 결과물에
  기입하지 않음. 요청이 있을 때만 표기. 대신 채널/카테고리로 구분.
- 이미지 처리 시 리사이즈(최대 1024px)로 API 비용/속도 관리.
- 입력은 폰 캡처가 전제이므로 HEIC(.heic/.heif)를 지원함(pillow-heif). EXIF 회전도
  실제 픽셀에 반영해서 전송함. 읽을 수 없는 입력은 조용히 건너뛰지 말고 멈출 것 —
  일부만 분석된 엑셀을 모르고 받는 것이 가장 나쁜 실패 방식임.
- 급하지 않은 대량 처리는 Batch API를 우선 검토할 것(요금 50%). 4단계 상세페이지
  분석도 같은 성격이라 배치가 적합할 가능성이 높음.
- API 호출은 `ant` CLI 경유를 유지할 것. API 키 발급·보관 없이 로그인만으로
  동작시키기 위한 의도적 선택임.
- 구조화된 결과가 필요한 곳에서는 프롬프트로 JSON을 부탁하지 말고 항상
  Structured Outputs(스키마 강제)를 쓸 것. 4단계 USP 분석처럼 정성적 요약이
  주인 작업이라도, 목록 형태로 정리되는 부분은 스키마로 받는 편이 안전함.
- 사용자는 개발 경험이 아주 많지는 않으므로, 코드 수정 시 변경 이유를 간단히
  설명하고 비유를 곁들이면 좋음.
