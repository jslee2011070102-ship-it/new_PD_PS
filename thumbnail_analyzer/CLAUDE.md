# 프로젝트 개요

이커머스(쿠팡 등) 생활용품 카테고리에서 경쟁 제품을 분석해, "가성비 포지셔닝"으로
신제품을 기획하기 위한 리서치 자동화 도구. 간헐적으로 (필요할 때마다) 실행하는
용도이며, 매번 처음부터 설명하지 않아도 되도록 이 파일에 맥락을 남겨둠.

## 전체 작업 흐름 (5단계)

1. 특정 채널·카테고리의 상위 20~25개 제품 썸네일을 폰으로 캡처
2. 썸네일에서 브랜드명/용량/구성/판매가/단위당단가/제품형태(용기·리필파우치·말통 등) 추출
   → **`analyze_thumbnails.py`로 구현 완료**
3. 추출된 데이터를 바탕으로 시장 내 우선 타겟 스펙(형태/용량/가격대) 도출
   → 사람이 엑셀 보면서 판단 (자동화 대상 아님, 매번 상황이 다름)
4. 타겟 제품군의 상세페이지를 통으로 캡처해서 USP 분석
   → **미구현, 다음 작업 대상**
5. 결과물을 엑셀 또는 제품기획서(docx) 형태로 출력

## 현재 구현 상태

### `analyze_thumbnails.py` (2단계, 완료)
- 폴더 안 이미지들을 하나의 배치로 묶어 Claude Vision(`claude-sonnet-5`)에 전달
- AI 역할: 이미지 속 텍스트 읽기 + 제품형태(본품/리필/말통) 시각적 판단만 수행
- **출력 형식은 Structured Outputs로 강제** — `ProductInfo`(pydantic) 스키마를
  `client.messages.parse(output_format=...)`에 넘기면, API가 스키마를 벗어난
  응답 자체를 만들지 못하게 막아줌. 덕분에 코드블록 제거·`json.loads`·파싱 실패
  처리가 전부 불필요해졌음. 추출 항목을 바꾸려면 `ProductInfo`만 고치면 됨
  (항목 설명도 `Field(description=...)`에 적으므로 프롬프트는 원칙만 담당).
- 타입을 스키마에 못박은 덕에(`price_krw: int | None`) 판매가에 쉼표나 '원'이
  섞여 들어오는 일이 없음 → 뒤의 나눗셈이 안전함
- **숫자 계산(단위당단가 등)은 반드시 파이썬 코드에서 처리** — AI가 산수를 틀리는 걸
  방지하기 위한 의도적 설계. 이 원칙은 앞으로 만들 스크립트에도 유지할 것.
- **호출 경로는 Anthropic 공식 CLI(`ant`)** — 파이썬이 요청 JSON을 만들어
  `ant messages:batches {create,retrieve,results}`에 stdin으로 넘김. 인증은
  `ant auth login`(OAuth 프로필)이 담당하므로 ANTHROPIC_API_KEY가 필요 없음.
  이 때문에 anthropic SDK 의존성도 없앰(스키마는 pydantic만으로 생성).
  주의: ANTHROPIC_API_KEY가 설정돼 있으면 프로필보다 우선하므로, 로그인 계정을
  쓰려면 해당 환경변수를 비워야 함.
- **Batch API 사용(요금 50%)** — 대신 즉시 응답이 아니므로 명령이 셋으로 나뉨:
  `submit`(제출) / `status`(진행 확인) / `fetch`(엑셀 회수).
  제출과 회수가 별개 실행이라, 그 사이 상태는 `.batch_jobs/<batch_id>.json`에 보관.
  이 파일에는 custom_id(img-0001 …) ↔ 원본파일명 매핑과 채널/카테고리/조사일자가 들어감
  (배치 결과는 순서가 보장되지 않고 custom_id로만 식별되므로 이 매핑이 필수).
  회수 완료 표시는 엑셀 저장에 성공한 뒤에만 기록 → 저장 실패 시 fetch 재실행으로 복구 가능.
- 배치는 24시간 내 미완료 시 만료(요금 미청구). 개별 요청 실패는 배치 전체를
  실패시키지 않으며, 실패·만료 사유는 해당 행의 비고란에 남음.
- 출력 엑셀은 회수할 때마다 기존 파일에 새 행을 이어붙임 (누적 데이터베이스처럼 사용).
  간헐적으로 실행되는 툴이라 세션 간 기억이 없으므로, 상태는 엑셀 파일 자체에 저장됨.
- 컬럼: 조사일자/채널/카테고리/원본파일명/브랜드명/제품명/판매가(원)/용량_원문/
  구성_원문/총용량/단위/단위당가격(원)/단가기준/쿠팡표기단가/단가검증/제품형태/제품역할/
  순위/순위_원문/리뷰수/월구매자수(명)/구매자수_원문/추정월매출(원)/형태_판단근거/비고
- **시장 지표**: 카테고리 순위, 리뷰수, 월구매자수를 함께 수집. 가격만으로는 시장
  위치를 볼 수 없어 추가함. 순위·구매자수는 원문 문구를 그대로 받아두고 파이썬이
  숫자를 뽑음('2만명' -> 20000 등 한글 단위 환산 포함).
- **'구매했어요' vs '만족했어요' 구분이 필수.** 쿠팡은 같은 자리에 두 문구를 번갈아
  보여주는데 '만족'은 구매자수가 아님. 코드가 문구에 '구매'가 있을 때만 숫자로
  인정하며, 아니면 월구매자수와 추정월매출을 비움(원문은 컬럼에 남겨 사람이 확인 가능).
  이 판정을 AI에게 맡기지 않는 이유는 매출 추정의 근거가 되는 값이기 때문.
- **추정월매출 = 월구매자수 x 판매가 x REVENUE_OPTION_MULTIPLIER(기본 2)**.
  한 상품 페이지에 여러 옵션이 묶여 있고 구매자수는 페이지 단위라 배수를 곱함.
  구매자수가 '이상'으로 끝나는 하한값이고 배수도 어림이므로 절대액으로 쓰지 말고
  제품 간 규모 비교용으로만 볼 것. 배수를 바꾸려면 해당 상수를 수정하거나
  엑셀에서 다시 곱하면 됨(구성 값이 모두 컬럼에 있음).
- **형태(겉모습)와 역할(본품/리필)은 반드시 별도 칸으로 둘 것.** 실제 쿠팡 데이터에서
  "말통 형태의 리필 제품"이 나와, 한 칸으로는 둘 중 하나를 잃어버림을 확인했음.
  `product_form`=용기/파우치/말통/기타, `product_role`=본품/리필/불명.
  역할은 제품명에 '본품'/'리필'로 적혀 있는 경우가 많아 시각 판단보다 정확함.
  같은 이유로 '세트'는 형태에서 제외함 — 수량은 `구성_원문`이 담당하는 별개 축임.
- **단위는 용량(ml/g)과 개수(개) 두 갈래.** 캡슐세제처럼 개수로 파는 카테고리가 있어
  `parse_capacity`가 '26개입' -> (26, '개')도 처리함. 기준은 `unit_price_basis`가 정함:
  액체는 100ml/100g당, 개수 제품은 1개당. 엑셀의 `단가기준` 컬럼에 어느 기준인지 표기됨.
  제품명이 '...,26개입, 1개' 형태이면 앞이 capacity_text(팩 크기), 뒤가
  composition_text(묶음 수량)임 — 액체의 '500ml, 4개'와 같은 구조.
- **단가 검산**: 쿠팡은 '(100ml당 1,190원)'을 화면에 이미 표시함. 이 표기를
  `unit_price_text`에 원문 그대로 읽어두고, 파이썬이 100 기준으로 환산해 우리 계산과
  대조함(`단가검증` 컬럼). 용량이나 가격을 잘못 읽으면 여기서 불일치로 드러나므로,
  추가 비용 없이 정확도를 검증할 수 있음. 읽기는 AI / 환산·비교는 코드 원칙 유지.

### 다음 작업: 4단계 — 상세페이지 USP 분석 (미구현)
- 입력: 상세페이지를 세로로 길게 캡처한 이미지(또는 여러 장으로 나뉜 이미지)
- 목적: 타겟 제품군의 상세페이지에서 반복적으로 등장하는 USP(성분/인증/차별점/
  프로모션 문구 등)를 뽑아서, 신제품 기획 시 "어떤 소구점을 넣을지" 참고자료로 삼음
- 2단계와 달리 이건 숫자 추출이 아니라 정성적 요약에 가까움 → 구조화 JSON보다는
  "USP 리스트 + 인용 근거" 형태의 출력이 적합할 가능성 있음 (착수 시 논의 필요)
- 최종적으로 2단계 엑셀 + 4단계 분석을 합쳐 5단계(엑셀 or 제품기획서 docx) 출력

### 수집 실적 (2026-09-21 기준)
- 쿠팡 6개 카테고리 x 25개 = 150건 수집 완료.
  세탁세제 / 캡슐세제 / 섬유유연제 / 섬유탈취제 / 주방세제 / 살균소독제.
- 단가검증 결과: 일치 145건, 표기없음 5건, **불일치 0건**.
  표기없음은 캡처 하단이 버튼 바에 가려 쿠팡 단가 표기가 안 찍힌 경우.
- 캡처 시 주의: 하단 '장바구니 담기' 바가 정가·단위당가격 표기를 가리는 일이
  잦음. 스크롤을 조금 더 내려서 찍으면 검산 가능 건수가 늘어남.
- 카테고리마다 단가 기준이 다름. 캡슐세제는 1개당, 주방세제 일부(트리오 14kg)는
  100g당, 나머지는 100ml당. `단가기준` 컬럼을 반드시 확인하고 비교할 것.

### 향후 아이디어: 대시보드 (미착수)
- 사용자 요청: 로컬 폴더를 대시보드에서 열어(업로드해) 분석을 돌리고 결과를 보는 형태.
- 착수 전 확인 필요: 브라우저는 보안상 로컬 경로를 직접 읽지 못함. 선택지는
  (a) 폴더 선택 UI로 파일을 읽어 올리는 웹앱(로컬 서버 + 브라우저 파일 선택),
  (b) 로컬에서 도는 데스크톱/로컬웹 앱(경로를 그대로 다룰 수 있음).
  현재 도구가 `ant` CLI와 로컬 상태파일(.batch_jobs)에 의존하므로 (b)가 더 자연스러움.
- 대시보드가 생기면 status/fetch를 사람이 명령으로 치지 않아도 되므로,
  배치 진행 상황 표시와 결과 열람이 주된 가치가 됨.

## 지켜야 할 제약/원칙

- 회사명(클라코리아/타이드웍스/담다다담/엘든코리아 등 운영주체명)은 결과물에
  기입하지 않음. 요청이 있을 때만 표기. 대신 채널/카테고리로 구분.
- 이미지 처리 시 리사이즈(최대 1024px)로 API 비용/속도 관리.
- 입력은 폰 캡처가 전제이므로 HEIC(.heic/.heif)를 지원함(pillow-heif). EXIF 회전도
  실제 픽셀에 반영해서 전송함. 읽을 수 없는 입력은 조용히 건너뛰지 말고 멈출 것 —
  일부만 분석된 엑셀을 모르고 받는 것이 가장 나쁜 실패 방식임.
- 급하지 않은 대량 처리는 Batch API를 우선 검토할 것(요금 50%). 4단계 상세페이지
  분석도 같은 성격이라 배치가 적합할 가능성이 높음.
- API 호출은 `ant` CLI 경유를 유지할 것. API 키 발급·보관 없이 로그인만으로
  동작시키기 위한 의도적 선택임.
- 구조화된 결과가 필요한 곳에서는 프롬프트로 JSON을 부탁하지 말고 항상
  Structured Outputs(스키마 강제)를 쓸 것. 4단계 USP 분석처럼 정성적 요약이
  주인 작업이라도, 목록 형태로 정리되는 부분은 스키마로 받는 편이 안전함.
- 사용자는 개발 경험이 아주 많지는 않으므로, 코드 수정 시 변경 이유를 간단히
  설명하고 비유를 곁들이면 좋음.
