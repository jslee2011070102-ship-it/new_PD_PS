# 가성비 제품기획 리서치 자동화 (인수인계 문서)

이커머스(현재는 쿠팡) 생활용품 카테고리의 경쟁 제품을 조사해서,
**"가성비 포지셔닝으로 신제품을 내려면 어떤 규격을 얼마에, 생산원가 얼마로
만들어야 하는가"** 에 답하기 위한 도구 모음이다.

특정 회사 전용이 아니라, 제품기획을 할 때 공통적으로 반복되는 조사 작업을
코드로 만들어 둔 것이다. 그래서 결과물에 운영주체명은 넣지 않는다(아래 규칙 참고).

---

## 1. 먼저 읽을 문서 (중복 설명을 피하기 위한 지도)

이 문서는 **저장소 전체의 지도와 인수인계 사항**만 담는다.
도구 사용법과 설계 배경은 아래 문서에 이미 정리돼 있으니 그쪽을 보면 된다.

| 알고 싶은 것 | 볼 문서 |
|---|---|
| 명령어를 어떻게 치는지, 엑셀 컬럼을 어떻게 읽는지 | `thumbnail_analyzer/README.md` |
| 왜 그렇게 설계했는지, 무엇을 조심해야 하는지 | `thumbnail_analyzer/CLAUDE.md` |
| 저장소 전체 구성 / 현재 진행 상태 / 인수인계 | **이 문서** |
| 공장 전달용 견적요청서를 다시 만드는 법 | 이 문서 5장 |

`CLAUDE.md`는 Claude Code가 세션마다 자동으로 읽는 프로젝트 메모리다.
사람이 읽어도 되지만, **설계 판단의 근거**가 주 내용이다.

---

## 2. 전체 작업 흐름과 현재 상태

| 단계 | 하는 일 | 담당 | 상태 |
|---|---|---|---|
| 1 | 카테고리 상위 25개 제품 썸네일 캡처 | 사람(폰/PC) | 수동 |
| 2 | 썸네일에서 가격·용량·순위·리뷰수 추출 → 엑셀 | `analyze_thumbnails.py` | **완료** |
| 3 | 엑셀을 보고 타겟 규격·가격대 판단 | 사람 + Claude | **완료(1회차)** |
| 4 | 상세페이지에서 USP 추출 | `analyze_details.py` | 도구 완성 / **데이터 미수집** |
| 5 | 최종 산출물(견적요청서·기획서) 출력 | `문서생성/` | **완료(견적요청서)** |

3단계를 자동화하지 않은 것은 의도적이다. 매번 카테고리 사정이 달라서
사람의 판단이 들어가야 하는 구간이다.

---

## 3. 폴더 구조

```
new_PD_PS/
├── README.md                     ← 이 문서
├── thumbnail_analyzer/           2단계·4단계 도구
│   ├── analyze_thumbnails.py       썸네일 → 가격/시장지표 엑셀
│   ├── analyze_details.py          상세페이지 → USP 엑셀
│   ├── requirements.txt
│   ├── README.md                   사용법
│   └── CLAUDE.md                   설계 배경 (프로젝트 메모리)
├── data/extracted/               1회차 추출 원본 (카테고리별 25건 x 6 = 150건)
├── 문서생성/                      5단계 산출물 생성기
│   ├── 견적요청서_데이터.json        12개 스펙 + 근거 데이터
│   ├── 견적요청서_생성.js            docx 생성 스크립트
│   └── package.json
└── 신제품_생산견적요청서.docx      생성된 결과물 (공장 전달용)
```

### `data/extracted/`를 커밋해 둔 이유
엑셀(`*.xlsx`)은 `.gitignore`로 제외했지만 이 JSON은 남긴다.
**이미지를 다시 읽지 않아도 엑셀을 언제든 다시 만들 수 있는 원본**이기 때문이다.
컬럼을 추가하거나 계산식을 고쳤을 때, 재촬영 없이 `build`만 다시 돌리면 된다.

비유하자면 JSON은 **필름 원본**이고 엑셀은 **인화된 사진**이다.
인화지는 버려도 되지만 필름은 보관한다.

## 4. 처음 받았을 때 준비

```bash
# 2·4단계 도구 (파이썬)
cd thumbnail_analyzer
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

# 5단계 문서 생성기 (Node)
cd ../문서생성
npm install
```

**API 키는 필요 없다.** 이미지를 읽는 일은 Claude가 대화 중에 직접 하고,
파이썬 스크립트는 그 결과를 검증·계산해서 엑셀로 만드는 역할만 한다.

## 5. 견적요청서 다시 만들기

가격 조건이 바뀌면 문서를 손으로 고치지 말고 데이터만 고친 뒤 다시 생성한다.

```bash
cd 문서생성
# 1) 견적요청서_데이터.json 에서 price / cost / spec 등을 수정
# 2) 다시 생성
node 견적요청서_생성.js
#    → ../신제품_생산견적요청서.docx 가 새로 만들어진다
```

`견적요청서_데이터.json`은 **12개 스펙의 배열**이다(카테고리 6개 x 본품·리필 2).
한 항목의 구성:

| 키 | 뜻 |
|---|---|
| `cat` / `role` / `form` | 카테고리 / 본품·리필 / 용기·말통·파우치 |
| `spec` / `qty` | 규격 문자열 / 낱개 수량 |
| `price` / `cost` / `costEach` | 목표 판매가 / 목표 생산원가 / 낱개 환산 원가 |
| `unit` / `basis` | 단위당 단가 / 그 기준(100ml당·1개당 등) |
| `benchBrand` `benchUnit` `benchDiff` | 기준으로 삼은 경쟁 제품과 대비율 |
| `why` | 그 규격을 고른 근거 (문서에 그대로 실림) |
| `evidence` | 문서에 실리는 경쟁사 단가표 |

**생산원가는 `price / 3.5`로 계산한 값을 넣는다.** 3.5배수 안에 쿠팡 수수료와
배송비가 이미 감안돼 있다는 전제이므로, 견적 단계에서 그걸 또 빼지 않는다.

## 6. 1회차 조사 결과 (2026-09 기준)

- **쿠팡 6개 카테고리 x 25개 = 150건 수집 완료**
  (세탁세제 / 캡슐세제 / 섬유유연제 / 섬유탈취제 / 주방세제 / 살균소독제)
- **단가 검산 결과: 일치 145건 · 표기없음 5건 · 불일치 0건**
  (쿠팡이 화면에 직접 표시하는 단가와 우리 계산을 대조한 것. 추가 비용 없이
  읽기 오류를 잡아내는 장치다. `표기없음`은 캡처 하단이 장바구니 바에 가려진 경우)
- 그 결과로 **12개 스펙(카테고리별 본품·리필)의 목표 판매가·생산원가**를 도출해
  공장 전달용 견적요청서로 만들었다.

### 목표 판매가를 정한 방식 (중요)
1. 같은 카테고리·같은 역할(본품/리필)의 단위당 단가를 싼 순으로 줄 세운다
2. 맨 앞 값이 그 다음 값보다 **1.5배 이상 싸면 버린다** — 시장에 한 곳뿐인
   특이값이라 가격대가 아니기 때문
3. 그렇게 남은 **실제 가격대의 최저가에서 약 5% 아래**를 목표가로 잡는다

2번을 넣게 된 계기가 있다. 처음에는 그냥 최저가를 기준으로 썼더니
섬유유연제에서 2위와 1.8배 차이 나는 단독 최저가에 끌려가,
**시장에 존재하지 않는 가격(6,900원)** 이 나왔다.
동네 시세를 보는데 급매물 한 건만 보고 시세를 적은 것과 같다.

## 7. 반드시 지켜야 할 규칙

1. **결과물에 운영주체 회사명을 넣지 않는다.** 요청이 있을 때만 표기한다.
   문서에는 채널(쿠팡)과 카테고리로만 구분한다.
2. **상품 URL을 추측해서 만들지 않는다.** 엉뚱한 상품으로 연결되면 없느니만
   못하다. 모르면 비워두고 `검색링크` 컬럼(제품명 기반 검색 주소)을 쓴다.
3. **숫자 계산은 전부 파이썬이 한다.** AI는 이미지의 글자를 읽는 것까지만 한다.
   매출·단가처럼 돈이 걸린 값을 AI 산수에 맡기지 않기 위한 설계다.
4. **`단가기준`이 다른 행끼리 단가를 비교하지 않는다.**
   캡슐세제는 `1개당`, 액체류는 `100ml당`이라 숫자를 직접 견주면 안 된다.
5. **"만족했어요"는 구매자수가 아니다.** 쿠팡이 같은 자리에 번갈아 보여주는
   다른 문구다. 코드가 '구매'가 있을 때만 숫자로 인정하도록 막아 두었다.
6. **쿠팡은 자동 수집이 막혀 있다**(서버 IP에서 403, 약관상으로도 금지).
   캡처는 사람이 하거나, 사용자의 브라우저에서 도는 Claude 확장을 쓴다.

---

## 8. 알려진 제약

- **상세페이지 USP 데이터가 아직 없다.** 도구(`analyze_details.py`)와
  수집 지시문은 완성돼 동작 확인까지 마쳤고, 캡처만 하면 바로 돌아간다.
  전수조사하지 말 것 — 썸네일 분석이 봐야 할 제품을 이미 골라준다(150 → 16개 사례).
- **추정월매출은 어림값이다.** `월구매자수 x 판매가 x 2`이고, 구매자수가
  "3만명 **이상**" 같은 하한이라 실제보다 낮게 나온다.
  절대 금액이 아니라 **제품 간 규모 비교용**으로만 쓴다.
- **생성된 docx를 이 작업 환경에서 화면으로 확인할 수 없다**(오피스 변환 도구가
  깨져 있음). 구조 검사까지만 가능하므로, PDF로 내보내기 전에 Word에서
  한 번 눈으로 훑어보는 절차가 필요하다.

## 9. 다음 사람이 이어서 할 일

1. 타겟 제품군 상세페이지 캡처 → 4단계 USP 분석 실행
2. 2단계 엑셀 + 4단계 USP를 합쳐 **제품기획서(docx)** 생성 (5단계 확장)
3. (선택) 대시보드 — 로컬 폴더를 열어 분석을 돌리고 결과를 보는 형태.
   브라우저는 보안상 로컬 경로를 직접 못 읽으므로, 로컬에서 도는 앱 형태가 자연스럽다.
